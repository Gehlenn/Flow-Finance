## Veredito

O baseline tinha apenas dois `any` sintáticos reais em produção, ambos em `components/CashFlow.tsx`. Eles apagavam justamente o contrato que mais precisava de validação: relatório estratégico vindo de IA ou `localStorage`.

Também havia 18 casts duplos `as unknown as`. Treze eram removíveis com alta confiança porque o código ou os typings instalados já forneciam um contrato melhor. Os cinco restantes estão concentrados em `src/services/sync/cloudSyncClient.ts`; removê-los apenas com tipos estáticos faria o HTTP/Firestore parecer validado sem que haja schema por entidade.

Resultado desta frente:

- `any` em produção: **2 → 0**;
- casts duplos: **18 → 5**;
- index signatures com valor `any`: **0 → 0**;
- `unknown`: **435 → 419**, mantido quando representa dado ainda não validado;
- type-check da aplicação e do backend: **PASS**;
- testes focados: **15 arquivos e 76 testes, todos passando**.

## Assessment crítico

### 1. O problema real não era volume de `any`

O repositório já havia passado por uma limpeza ampla. Restaram somente dois `any`, mas ambos contaminavam:

- o estado React do relatório estratégico;
- o resultado de `JSON.parse`;
- a resposta variável do backend/IA;
- a renderização e compartilhamento do relatório.

Essa concentração era mais importante que a contagem absoluta. Um payload malformado podia ser armazenado e depois tratado como relatório renderizável.

### 2. Havia casts escondendo contratos que já existiam

Casos como OFX, Vite env, Redis e persistência JSON não precisavam de casts duplos:

- `parseOFX()` já retorna `Transaction[]`;
- as chaves Sentry podem ser projetadas explicitamente de `import.meta.env`;
- o cliente Redis pode ser adaptado para a interface mínima consumida;
- `saveJsonState()` já aceita `unknown`;
- o módulo Tesseract pode ser descrito por `typeof import('tesseract.js')`.

### 3. Um cast escondia incompatibilidade real de pacote

`src/engines/importacao/pdfExtrato.ts` tratava `pdf-parse` como uma função default legada. O pacote instalado é `pdf-parse@2.4.5`; seus arquivos `package.json`, `PDFParse.d.ts`, `LoadParameters.d.ts` e `TextResult.d.ts` declaram:

- export nomeado `PDFParse`;
- construtor com `LoadParameters`;
- `getText(): Promise<TextResult>`;
- `destroy(): Promise<void>`.

O cast duplo fazia o TypeScript aceitar uma API que o pacote instalado não oferece. A implementação agora usa a classe oficial, passa bytes tipados, lê `TextResult.text` e encerra o parser.

### 4. Cinco casts de sync não podem ser apagados honestamente ainda

`cloudSyncClient` recebe:

- `EntityState` tipado no caminho Firestore;
- `Record<string, unknown>` no caminho HTTP;
- um `PullResponse<TPayload>` genérico que perde o vínculo entre nome da coleção e tipo do payload.

Trocar esses casts por `Account[]`, `Transaction[]` etc. sem validar o payload do backend seria apenas uma mentira estática mais elegante. A correção exige mapa por entidade e validators no boundary HTTP.

## Pesquisas e contratos usados

### Contratos locais do código

- `backend/src/types/index.ts` declara o relatório estratégico do backend como `summary` + `actions`.
- `services/geminiService.ts` e a demo local usam `executiveSummary` + `actionPlan`.
- `src/finance/ofxParser.ts` retorna `Transaction[]` com `description` e `merchant` já normalizados.
- `backend/src/services/persistence/postgresStateStore.ts` recebe `payload: unknown` em `saveJsonState`.
- `backend/src/services/clinic/IdempotentEventStore.ts` depende apenas da interface mínima `RedisLike`.

### Typings instalados dos pacotes

- `pdf-parse@2.4.5`: `PDFParse`, `LoadParameters`, `TextResult`.
- `tesseract.js@7`: `recognize(image: ImageLike, ...)`.
- `redis@5.11`: métodos usados pelo adapter (`get`, `set`, `setEx`, `exists`, `del`, `keys`, `ttl`, `ping`).
- Vite: `ImportMetaEnv`; as chaves específicas do Flow são projetadas explicitamente para `SentryEnv`.

Não foi necessário usar documentação secundária ou inventar contratos externos.

## Mudanças de alta confiança implementadas

### Relatório estratégico do Cash Flow

- Estado alterado de `any` para `StrategicReport | null`.
- `normalizeStrategicReport()` agora recebe `unknown`.
- Guard de record e leitura de strings impedem acesso antes de narrowing.
- JSON armazenado é tratado como `unknown` e validado antes de entrar no estado.
- O normalizador aceita os dois formatos comprovados no repositório:
  - frontend/demo: `executiveSummary` + `actionPlan`;
  - backend: `summary` + `actions`.
- O estado renderizável tem `executiveSummary`, `actionPlan` e `diagnostic` obrigatórios.
- Payload incompleto continua virando fallback explícito, sem esconder a indisponibilidade.

### Casts duplos removidos

- `CashFlow`, `TransactionList` e `Assistant` agora usam narrowing com o operador `in` para metadados opcionais, sem converter a entidade inteira em record.
- Sentry projeta as chaves usadas de `import.meta.env` para `SentryEnv`.
- OFX consome diretamente o `Transaction` retornado pelo parser.
- OCR usa `typeof import('tesseract.js')`, `Parameters<...>` e uma union explícita para o fallback textual.
- O controller de clínica adapta o cliente Redis para `RedisLike` método a método.
- Workspace e SaaS passam o estado diretamente para `saveJsonState(payload: unknown)`.
- PDF usa a API tipada real de `pdf-parse@2.4.5`.

## Ocorrências legítimas mantidas

- `catch (error: unknown)` e helpers de erro.
- `Record<string, unknown>` em JSON, Firestore, logs, eventos, metadados de billing e payloads de integração.
- `unknown` em fila/memória de IA onde o tipo do resultado depende do tipo da tarefa e ainda não existe discriminação completa.
- index signatures de envelopes deliberadamente extensíveis.
- cinco casts duplos em `cloudSyncClient`, adiados até existir validação por entidade.
- `safeJsonParse<T>()` e `loadJsonState<T>()` no backend, que ainda confiam no caller; endurecê-los exige migração coordenada dos consumidores e seus schemas.

## Recomendações

1. Criar um mapa de payload por `SyncEntity` e validators por entidade no retorno HTTP antes de remover os cinco casts restantes de sync.
2. Migrar `safeJsonParse<T>()` e `loadJsonState<T>()` para retorno `unknown`, fazendo cada consumidor validar antes de construir o domínio.
3. Alinhar formalmente o contrato de relatório estratégico entre frontend e backend. O normalizador atual preserva compatibilidade, mas o ideal é um schema de resposta único.
4. Manter `unknown` nos boundaries e medir separadamente:
   - `any`;
   - cast duplo;
   - acesso a JSON sem guard;
   - generic parse que afirma `T` sem validação.
5. Se este scan virar gate, executar AST sobre produção e falhar em `AnyKeyword`/cast duplo novo, com allowlist curta apenas para boundaries documentados.
