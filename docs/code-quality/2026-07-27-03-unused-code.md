# 03 - Código, exports e dependências não usados

Data: 2026-07-27  
Escopo: frontend Vite/React, backend Express, scripts, testes, Vite/Vitest/Playwright, Capacitor, Vercel, Firebase Rules e CI.

> Nota de integração final: a reexecução do Knip com os loaders dinâmicos de
> Vite/Vitest desativados e os testes registrados como entradas estáticas
> revelou um subsistema paralelo de importação referenciado apenas por seus
> próprios testes. A integração removeu mais sete arquivos rastreados
> (`extratoImporter`, `ocrRecibo`, `pdfExtrato` e o teste unitário externo de
> `pdfExtrato`) e a dependência `pdf-parse`. O total combinado dos oito tracks é
> de 59 arquivos rastreados e 15 dependências diretas removidos.

## Resultado

- 50 arquivos removidos após confirmação por grafo e busca textual.
- 14 dependências diretas removidas dos manifests.
- 22 funções/wrappers mortos removidos de módulos ainda vivos, além de exports internos fechados.
- Um import de teste inválido corrigido.
- A varredura do snapshot desta frente ficou sem arquivo órfão e sem import não resolvido.
- Dois reports de dependência permanecem como falsos positivos documentados.

## Configuração e comandos

Foi adicionado `knip.json` com dois workspaces explícitos:

- raiz: `index.html`, `index.tsx`, configs Vite/Vitest/Playwright/Capacitor/PostCSS, scripts, testes e assets JavaScript de `public/`;
- backend: `api/index.ts`, `src/index.ts`, scripts, testes e módulos `src/**/*.test.ts`.

Isso é necessário porque o backend tem `package.json` próprio, mas não estava declarado como workspace npm, e porque scripts/testes/configs são entradas fora do grafo iniciado por `index.tsx`. A configuração segue o contrato de `entry`, `project` e workspaces do [Knip](https://knip.dev/reference/configuration).

Comandos principais:

```powershell
npx --yes knip@5.80.0 --include files,dependencies,unlisted,unresolved --reporter compact --no-progress --cache
npx --yes knip@5.80.0 --include exports,types,classMembers --reporter compact --no-progress --max-show-issues 250 --cache
rg -n -F <caminho-ou-simbolo> --glob '!node_modules/**' --glob '!dist/**' .
npm ls <dependencias> --all
npm --prefix backend ls <dependencias> --all
```

Cada candidato foi conferido contra:

- imports estáticos e dinâmicos;
- lazy imports do React;
- testes e mocks;
- scripts de `package.json`;
- workflows em `.github/workflows`;
- entradas Vercel e Capacitor;
- assets referenciados por `index.html` e service worker;
- histórico e documentos de auditoria que registravam remoções anteriores.

O report do Knip não foi usado como autorização automática para apagar.

## Assessment crítico

### 1. A documentação de cleanup tinha divergido do checkout

`docs/CODE_QUALITY_CLEANUP_2026-04-30.md` registrava como removidos o par de previsões, `goalService`, o script de ativação do Sentry, `public/index.css` e dois helpers de segurança. Esses artefatos estavam novamente no checkout. O review de segurança de 2026-06-27 também confirmava que a UI de previsões não tinha import de runtime.

Consequência: a documentação histórica estava correta sobre a decisão, mas não provava mais o estado atual. Esta rodada refez a prova no grafo vivo antes de restaurar a remoção.

### 2. Havia três tipos diferentes de código morto

1. Arquivos sem nenhum consumidor, incluindo esqueletos antigos de backend, barrels e domínios paralelos.
2. Ilhas alcançadas apenas pelos próprios testes, mas sem entrada de runtime, como a UI de previsão, `goalService` e `openBankingState`.
3. Exports públicos sem consumidor em arquivos ainda vivos.

Tratar testes como entradas evita falsos positivos, mas também faz uma ilha test-only parecer viva. Por isso a análise de runtime foi cruzada manualmente com os imports do app.

### 3. Os manifests misturavam fronteiras de execução

O backend declarava Capacitor, Sentry React e bcrypt sem import correspondente. A raiz declarava um segundo SDK Gemini, bibliotecas internas do Vite e Supertest apesar de os consumidores reais estarem no backend.

`fdir`, `picomatch` e `rollup` continuam disponíveis transitivamente por Vite/Vitest quando necessários; a correção removeu apenas a declaração direta sem consumidor. Isso limpa ownership do manifest, mas não deve ser apresentado como remoção completa dessas bibliotecas do lock transitivo.

### 4. O inventário de exports ainda precisa de passadas por contrato

O scan final ainda reporta:

- 76 exports;
- 42 tipos exportados;
- 14 membros públicos de classe.

Esses itens não foram apagados em massa. O conjunto mistura API pública, contratos de integração/clinic, aliases default/named, helpers usados por reflexão/configuração e funções financeiras que exigem testes de contrato antes de estreitar a superfície.

## Recomendações

1. Tornar a configuração do Knip um gate periódico, mas manter a confirmação manual para imports dinâmicos e contratos externos.
2. Auditar os 76/42/14 reports de superfície exportada por domínio. Prioridade: aliases legacy/default e wrappers puros; não começar por clinic, billing, auth ou persistência.
3. Separar o backend como workspace npm real ou documentar formalmente por que os dois manifests continuam independentes.
4. Executar `npm ci` limpo na integração central. O `node_modules` desta sessão ainda contém pacotes removidos como `extraneous` porque os locks foram atualizados sem prune para não interferir nos processos concorrentes.
5. Manter a distinção explícita entre “referenciado por teste” e “alcançável em runtime”; testes não devem preservar indefinidamente uma feature que saiu do produto.

## Riscos residuais

- O inventário de exports não está zerado; os itens restantes não tinham confiança suficiente para remoção transversal nesta frente.
- O Knip global precisa ser repetido após a integração dos três arquivos de tipos criados pela frente concorrente de ciclos.
- O teste completo e coverage global ficaram para a integração central devido à execução simultânea dos oito tracks; os type-checks completos, build e 83 testes focados ficaram verdes.
- Uma instalação limpa pode alterar o layout físico de dependências transitivas, embora os manifests e lockfiles estejam consistentes e o build atual tenha passado.
